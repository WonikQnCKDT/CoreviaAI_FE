# 프로젝트 화면의 부서 확장 경계

상태 Active · 범위 CoreviaAI_FE · 검토일 2026-11-18

[SCRUM-116](https://jnu-team-aaptc1y6.atlassian.net/browse/SCRUM-116)과 [전사관리 요구사항 NFR-15 및 4.14](https://jnu-team-aaptc1y6.atlassian.net/wiki/spaces/CoreviaAI/pages/8126909)를 기준으로 한다.

## 배경

프로젝트 메뉴와 라우터가 개별 페이지를 각각 선언하면 부서 기능을 추가할 때 양쪽을 수정해야 한다. 확장 화면이 공유 저장소를 직접 읽으면 작업 데이터와 권한 경계가 저장소 구현에 묶인다.

## 결정

- 부서 확장은 `src/extensions/<모듈>/`의 `DepartmentProjectModule`로 선언하고 `src/app/projectModules/projectModules.ts`에 등록한다. 선언에서 부서 유형·운영 방식·액터로 적용 조건을 지정하고, 첫 페이지를 메뉴 진입점으로 삼는다. 경로는 프로젝트 아래 정적 소문자 슬러그로 작성한다.
- 프로젝트 레이아웃과 라우터가 같은 등록 결과를 사용한다. 기본 경로와 충돌하는 경로, 중복 ID와 경로를 시작 시 거부한다. 서버 프로젝트의 부서 확장 적용 여부는 상세 조회가 성공한 뒤 평가한다.
- 확장 페이지는 `ProjectModuleProps`의 프로젝트 범위와 업무·리스크 점수·알림 읽기 인터페이스로 데이터를 받는다. ESLint는 확장에서 저장소·목업·기존 화면·네트워크 구현으로 직접 접근하는 import를 차단한다.
- 현재 데모 어댑터는 현재 프로젝트의 데이터만 반환한다. API 모드에서 실제 업무·점수·알림 데이터 공급자가 연결되기 전에는 빈 업무·알림과 미산정 점수(`null`)를 반환한다. 기존 화면의 표시 정책은 각 화면이 유지한다.
- 서버 DTO의 신규 부서·방법론·액터 값은 소문자 키로 모듈 프로필에 전달한다. 기존 프로젝트 화면에서 이미 사용하는 값은 기존 키를 유지한다.

## 대안과 영향

중앙 라우터에 부서별 조건문을 늘리는 방식은 페이지와 메뉴의 동기화 부담을 남긴다. 범용 플러그인 로더나 브라우저 웹훅을 도입하는 방식은 MVP에 필요한 코드 내 등록보다 운영 비용이 크다. 대신 모듈을 앱에서 조립하고, 새 데이터 공급자가 필요할 때 앱 어댑터에서 동일한 인터페이스로 전달할 수 있도록 했다.

제조 UI와 실제 QMS·MES, 웹훅은 별도 연동 범위다. 운영 데이터, 접근 권한, 외부 서비스 인증과 웹훅 수신은 서버 경계에서 검증한다. 새로운 운영 방식이나 액터의 생성·저장에는 해당 BE 계약과 생성 화면 선택지의 지원이 필요하다.

`npm test`에서 모듈 진입, 데이터 범위, 중복 경로, 적용 조건, 금지된 의존성을 확인한다.
